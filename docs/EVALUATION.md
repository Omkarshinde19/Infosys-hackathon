# Evaluation results

Generated by `./netheal eval` (300 held-out scenarios × 5 policies, 60 s of simulated time each). Raw runs and the summary: `docs/evaluation.json`; charts on the dashboard's Evaluation page.

Policies: `no_heal` detects and diagnoses only. `reactive` diagnoses with rules and applies the first detour, with no twin test and no guardrails. `twin` is NetHeal: rules + GNN diagnosis, twin-tested candidates behind the OPA guardrails. `predictive_twin` adds the forecaster and LSTM autoencoder. `rl` also adds the RL routing agent's proposal as one more candidate, tested like the rest (the live configuration).

## Reading these numbers

- `reactive` can recover a few more faults than `twin`: it ignores the blast-radius guardrail (at most 5 flows moved automatically), e.g. it moves every flow off a flapping internet uplink at once. NetHeal hands those to a human on purpose.
- An overloaded access switch has no detour (the traffic starts there), so the rules escalate it. The RL agent sometimes *mitigates* it instead, moving the switch's flows onto less-loaded paths further up so latency is back within 10% of normal.
- Without the RL agent no fix is rolled back: in the simulator every detour around the fault works, so testing on the twin first can't beat a plain detour on recovery. The agent's mitigations are closer calls: some pass the twin but fail the 3 s check on the network and are rolled back, ending no worse than without the agent.
- A mitigation of a *gradually worsening* overload can pass its check and break later. NetHeal notices (3 s of broken traffic), plans once more and hands it to a human when there is no better fix. That is why `rl` heals more faults than it keeps recovered.
- The forecaster's value is earlier detection of gradual faults. Diagnosing earlier occasionally names the wrong cause first; it is corrected before anything is applied.
